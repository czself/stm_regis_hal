# 第 27 课：软件 I2C 与 EEPROM

## 1. 本课到底在学什么

### 1.1 表面现象

我们用 PB6（SCL）和 PB7（SDA）两个普通 GPIO，像控制灯泡开关一样手动拉高拉低它们，拼出一段 AT24C02 能理解的 I2C 波形，向它写入 3 个字节：

```text
START -> 0xA0 -> 0x00 -> 0x5A -> STOP
```

PC13 上的 LED 每秒翻转一次，表示程序在持续运行。

### 1.2 这节课最核心的一个认识

**I2C 的本质不是某个外设，而是一套"什么时候把哪根线拉高/拉低"的规则。**

第 26 课用 I2C1 外设时，硬件自动按这套规则控制 SCL/SDA。但规则本身并不绑定 I2C1——只要你的代码能让 SCL/SDA 上的电压变化符合这套规则，任何设备都能看懂。

打个比方：
- 硬件 I2C = 自动挡汽车。你踩油门（写寄存器），变速箱自动换挡（外设自动产生 START/SCL/STOP）。
- 软件 I2C = 手动挡汽车。你亲手踩离合、换挡杆推每个档位（用 GPIO 拼出每个电平变化）。

**到硬件层面，AT24C02 根本不知道信号来自 I2C1 外设还是 GPIO。它只认 SCL/SDA 上的波形。**

### 1.3 所以这节课你要盯住这条链路

```
C代码（写寄存器）→ GPIO 寄存器（BSRR/BRR）→ 引脚电压（3.3V / 0V）→ 总线波形 → AT24C02 识别
```

每一条 `GPIOB->BSRR = GPIO_BSRR_BS7` 都不是"抽象的配置"，而是实实在在地改变了 PB7 引脚上的电压。AT24C02 的 SDA 脚就接在 PB7 上，它"看"到电压变化就知道你在发数据。

### 1.4 但是——这节课有重要的边界

当前代码**只做了一件事**：发送波形。它没有验证 EEPROM 是否真的收到了。

- 没有读 ACK：第 9 个时钟释放 SDA 就不管了，不看从机是否拉低
- 没有读回校验：写完后不读回来比较

所以 PC13 翻转**只能证明**程序在跑、波形在发，**不能证明** EEPROM 写进去了。后面所有解释里，这个边界会反复出现。

## 4. 实验硬件

- 开发板：STM32F103C8T6 BluePill
- 下载器：ST-Link
- 外部模块：AT24C02 EEPROM
- 软件 I2C 引脚：PB6 = SCL，PB7 = SDA
- LED：PC13，常见 BluePill 为低电平点亮

接线：

```text
AT24C02 VCC -> 3.3V
AT24C02 GND -> GND
AT24C02 SCL -> PB6
AT24C02 SDA -> PB7
```

SCL/SDA 需要上拉电阻。HAL 版启用了内部上拉，但工程上更推荐外部 4.7k 左右上拉，因为 I2C 的上升沿质量直接影响通信可靠性。

## 5. 先建立一个最基本的脑图

### 5.1 整节课的执行路线

```text
一、准备工作（已学过，快速过）
   打开 GPIOB 时钟 → PB6/PB7 配成开漏输出 → 释放总线（SCL/SDA 都变高）

二、发送一个字节（本课核心）
   i2c_start()
     SDA=高, SCL=高 → 等一会儿 → SDA=低 → 等一会儿 → SCL=低
     波形：SCL=高时 SDA 从高跳低 → AT24C02 知道“要开始通信了”

   i2c_write_byte(0xA0) —— 器件地址 + 写方向
     循环 8 次，每次：
       ① 把当前 bit 放到 SDA（高或低）
       ② 拉高 SCL → AT24C02 在 SCL 高时采样 SDA 的电平
       ③ 拉低 SCL → 准备下一位
     第 9 个时钟：释放 SDA → 拉高 SCL → 拉低 SCL
     （本课不读 SDA，所以不知道 AT24C02 有没有 ACK）

   i2c_write_byte(0x00) —— EEPROM 内部地址
   i2c_write_byte(0x5A) —— 要写入的数据

   i2c_stop()
     SDA=低, SCL=高 → 等一会儿 → SDA=高
     波形：SCL=高时 SDA 从低跳高 → AT24C02 知道“传输结束”

三、收尾
   翻转 PC13 → 等 1 秒 → 回到二、重复
```

### 5.2 关键理解

**整条链路的核心只有两根线和一个规则**：

- **两根线**：SCL（时钟线）和 SDA（数据线）
- **一个规则**：SCL 高电平时，从机（AT24C02）读取 SDA 上的电平是 0 还是 1；SCL 低电平时，主机可以改变 SDA 的值

硬件 I2C 外设把上面这个流程封装成了“写 DR 寄存器→自动产生 START→自动移位→自动产生 SCL→自动检查 ACK”。而软件 I2C 就是用 GPIO 手动重现这个流程的每一步。

**没有魔法，只有电平变化。**

## 6. 核心名词解释

### 6.1 已学名词速查

以下名词在第 26 课（硬件 I2C + EEPROM）中已完整讲解，本课只用不重复展开：

| 名词 | 一句话提醒 |
|------|-----------|
| `开漏输出` | 只能拉低不能推高，高电平靠上拉电阻；I2C 总线电气基础，多个设备安全共享 |
| `PB6 / PB7` | F103 I2C1 默认引脚；本课仍用这两个脚，但不交给 I2C1 外设，由软件直接控制 |
| `START` | SCL 高时 SDA 从高变低，标志一次 I2C 传输开始 |
| `STOP` | SCL 高时 SDA 从低变高，标志本次传输结束 |
| `ACK` | 第 9 个时钟接收方拉低 SDA 表示应答；主机需释放 SDA 让从机有机会拉低 |
| `AT24C02` | 2Kbit I2C EEPROM，256 字节，7 位地址 0x50（A0/A1/A2 接地时） |
| `0xA0` | AT24C02 写地址字节 = 7 位地址 0x50 左移 1 位 + 写方向位 0 |
| `GPIOB` | PB6/PB7 的寄存器组，通过 `CRL` 配置模式，`BSRR`/`BRR` 控制电平 |
| `GPIOB->CRL` | GPIOB 低 8 位引脚（含 PB6/PB7）的配置寄存器，`MODE=11` + `CNF=11` = 开漏输出 |
| `RCC->APB2ENR` | APB2 外设时钟使能，GPIOB 的时钟位是 `IOPBEN` |
| `BSRR / BRR` | BSRR 写 1 置高（开漏下为释放），BRR 写 1 拉低 |

### 6.2 `软件 I2C` 是什么

#### 6.2.1 先搞清一个问题：I2C 协议 ≠ I2C 外设

第 26 课用的是 STM32 芯片内部一个叫 **I2C1** 的硬件模块。你告诉它"发 0xA0"，它自动产生 START、自动把 0xA0 的 8 个 bit 逐个放到 SDA 上、自动产生 SCL 时钟、自动检查 ACK。

而**软件 I2C** 完全不用 I2C1 这个硬件模块。它只用 PB6 和 PB7 两个普通 GPIO 引脚，由你的 C 代码直接控制这两个引脚的电平，按照 I2C 协议的规则一点一点地"造"出波形。

#### 6.2.2 怎么"造"？

关键理解：**每个 I2C 波形上的变化，在软件 I2C 里就是一条 GPIO 寄存器写语句。**

对照看：

| 波形上的变化 | 寄存器版代码 | 硬件的实际动作 |
|-------------|-------------|---------------|
| SDA 从高变低 | `GPIOB->BRR = GPIO_BRR_BR7` | PB7 引脚电压从 3.3V → 0V |
| SDA 从低变高(释放) | `GPIOB->BSRR = GPIO_BSRR_BS7` | PB7 引脚的下拉管关闭，上拉电阻把电压拉到 3.3V |
| SCL 从低变高 | `GPIOB->BSRR = GPIO_BSRR_BS6` | PB6 引脚电压从 0V → 3.3V |
| SCL 从高变低 | `GPIOB->BRR = GPIO_BRR_BR6` | PB6 引脚电压从 3.3V → 0V |

**也就是说，你每执行一条 `GPIOB->BSRR = ...` 或 `GPIOB->BRR = ...`，AT24C02 的 SCL/SDA 引脚上的电压就会变化一次。**

#### 6.2.3 为什么软件 I2C 能工作这么"底层"还能工作？

因为 I2C 这个协议本身只是规定了"什么时候 SCL 要高、什么时候 SDA 要变"，它**没有规定**这些信号必须由专门的 I2C 硬件产生。AT24C02 根本不关心信号是从 I2C1 模块出来的还是从普通 GPIO 出来的——它只认电压。

这就像两个人用摩斯密码通信：你用手电筒（GPIO）和用信号机（I2C 外设）发出的信号，对方收到是一样的，只要闪灯的频率和长短符合规则。

#### 6.2.4 软件 I2C 的优缺点

- **优点**：任何 GPIO 都可以当 I2C 用，引脚选择灵活；代码完全透明，你能看到协议每一步的细节
- **缺点**：CPU 全程参与（占 CPU），速度受延时循环精度限制，没有硬件自动处理 ACK/超时/总线冲突

#### 6.2.5 配错会怎样

如果把开漏输出错配为推挽，SDA 在第 9 个时钟无法被从机拉低。从机即使想发 ACK 也无法在电气上实现，因为主机在强推高 SDA。而本课代码又不读 SDA，所以表现为"代码照跑、LED 照闪、波形照发"，但 EEPROM 实际没写入。这种"无声失败"最难排查。

### 6.3 `SDA_HIGH()` / `SDA_LOW()` / `SCL_HIGH()` / `SCL_LOW()` 是什么

#### 6.3.1 从引脚到代码

PB6 和 PB7 是两个物理引脚。你拿万用表量 PB6 和 GND 之间的电压：代码写 `BSRR`（置位寄存器）时量到 3.3V，写 `BRR`（复位寄存器）时量到 0V。

软件 I2C 把"拉高这个引脚"和"拉低这个引脚"包装成了四个宏：

```c
/* PB7（SDA）相关 */
#define SDA_HIGH()   (GPIOB->BSRR = GPIO_BSRR_BS7)   /* SDA = 高（释放） */
#define SDA_LOW()    (GPIOB->BRR  = GPIO_BRR_BR7)    /* SDA = 低（拉低） */

/* PB6（SCL）相关 */
#define SCL_HIGH()   (GPIOB->BSRR = GPIO_BSRR_BS6)   /* SCL = 高 */
#define SCL_LOW()    (GPIOB->BRR  = GPIO_BRR_BR6)    /* SCL = 低 */
```

#### 6.3.2 开漏模式下的"高"不是推高，是释放

这里最容易搞混的一点：

在**推挽输出**模式写 `BSRR`，引脚被强行推到 3.3V——像开关直接连通电源。
在**开漏输出**模式写 `BSRR`，引脚被"释放"——像开关断开，靠外部电阻把电压拉上去。

所以 `SDA_HIGH()` 准确的物理含义是：
1. 关闭 PB7 内部的下拉管（不再把 SDA 拉到 GND）
2. 外部上拉电阻把 SDA 线的电压拉到 3.3V
3. AT24C02 的 SDA 引脚也接到了这根线上，所以它也测到 3.3V

而 `SDA_LOW()` 的物理含义是：
1. 打开 PB7 内部的下拉管
2. SDA 线被强制拉到 GND（约 0V）
3. AT24C02 的 SDA 引脚也测到 0V

**为什么非得这样？** 因为 I2C 允许多个设备共享 SDA 线。如果一个设备想输出高、另一个想输出低，推挽模式下两个设备会"打架"（一个拼命推 3.3V，一个拼命拉 0V，电流过大可能烧引脚）。开漏模式下，谁想输出 0 就拉低，谁想输出 1 就"撒手"（释放），这样永远不会冲突。

#### 6.3.3 这些宏在 I2C 传输中怎么用

整个 I2C 传输就是反复调用这四个宏，只是调用的顺序和时机不同：

- **START 条件**：`SDA_HIGH()` → `SCL_HIGH()` → `SDA_LOW()` → `SCL_LOW()`
- **发一个 bit=1**：`SDA_HIGH()` → `SCL_HIGH()` → `SCL_LOW()`
- **发一个 bit=0**：`SDA_LOW()` → `SCL_HIGH()` → `SCL_LOW()`
- **STOP 条件**：`SDA_LOW()` → `SCL_HIGH()` → `SDA_HIGH()`

注意规律：SCL 高电平时 AT24C02 才采样 SDA，所以每次都要在拉高 SCL 之前先把 SDA 设好。

#### 6.3.4 配错会怎样

如果 `soft_i2c_delay()` 的循环次数不够（延时太短），SCL 高电平保持时间不足，AT24C02 内部的采样电路来不及稳定读取 SDA 的电平，就会出现"发了 1 但 AT24C02 读成了 0"或反过来。如果 SCL 和 SDA 的顺序搞反（比如先拉高 SCL 再设 SDA），AT24C02 在 SCL 高时读到的是 SDA 的旧值，不是当前 bit 的值。

### 6.4 `delay_cycles()` 是什么

软件 I2C 的速度由延时决定。`delay_cycles()` 内部循环执行 `__NOP()`，让 SCL/SDA 的电平保持足够时间。

它属于 C 软件时序层。系统时钟变了，实际 I2C 速度也会跟着变，因为延时循环不是硬件定时器。

本课为什么需要它：软件 I2C 不像硬件 I2C 有 `CCR` 寄存器精确控制 SCL 频率。延时函数直接决定了 SCL 每个高/低电平的持续时间，也就决定了 I2C 通信速率。

配错会怎样：`delay_cycles(120)` 在 72MHz 下约产生 1.6µs 延时。如果参数设得太小（如 `delay_cycles(1)`），SCL 频率远高于 AT24C02 能支持的上限，从机无法正确采样。设得太大则通信极慢，但不影响正确性。

### 6.5 `HAL_GPIO_WritePin()` 是什么

HAL 版用它设置 PB6/PB7 输出状态。

在开漏输出模式下，写 `GPIO_PIN_SET` 表示释放总线，写 `GPIO_PIN_RESET` 表示拉低总线。它对应寄存器版的 `BSRR/BRR` 写操作。

本课为什么需要它：HAL GPIO API 把寄存器操作封装成统一的函数接口。理解 `GPIO_PIN_SET` 在开漏模式下不是"强推高"而是"释放"，才能正确理解 HAL 版代码中的 `sda_write(GPIO_PIN_SET)` 和寄存器版 `SDA_HIGH()` 是同一件事。

配错会怎样：在需要释放 SDA 的时机（如 ACK 位）错误地写 `GPIO_PIN_RESET`，就会把 SDA 强拉低，从机无法拉低 ACK、总线被主机一直占用，从机发不出应答。

### 6.6 `AT24C02 写周期` 是什么

AT24C02 这类 EEPROM 收到写命令后，不是 STOP 一出现就立刻完成内部存储。它还需要一个内部写周期，把数据真正写入非易失存储单元，这个时间通常是毫秒级。

本课为什么需要它：当前代码每秒发送一次写序列，间隔很长，所以通常不会撞上写周期。但如果你改成连续快速写多个地址，就必须在写后延时，或者用 ACK polling 不断发送器件地址，直到 EEPROM 再次 ACK。否则下一次写或读可能发生在器件忙碌期间。

配错会怎样：连续写入而不等待写周期，EEPROM 可能不响应第二次操作（不发 ACK），代码如果没补 ACK 判断就表现为"看起来在发波形，但数据没写进去"。

### 6.7 `读回校验` 是什么

读回校验是写 EEPROM 后再读同一地址，确认读出的值是否等于刚才写入的值。

本课为什么需要它：当前代码没有读函数，所以不能做校验。完整 EEPROM demo 至少应包含：写地址和数据、等待写周期、重新发送地址、读回数据、比较结果。没有这一步，LED 翻转和波形存在都只能证明"主机尝试写了"，不能证明"EEPROM 保存了"。

配错会怎样：不做读回校验时，SCL/SDA 有波形不等于 EEPROM 确实收到了数据。例如 EEPROM 地址脚与 `0xA0` 不匹配时，从机不会 ACK，但代码又不读 ACK，波形照发，LED 照闪，你完全不知道写失败了。

## 7. 寄存器版代码逐步讲解

### 7.1 已学步骤（快速过）

以下三步在前 4 课和第 26 课已完整讲解，本课不再逐条拆解：

- **系统时钟**：`system_clock_72mhz_init()` 配置 HSE+PLL → 72MHz。软件 I2C 没有 `CCR` 这类硬件分频寄存器，所以系统时钟变化会直接影响 `delay_cycles()` 的真实时间。系统时钟越快，软件 I2C 也越快。
- **PC13 LED**：`pc13_led_init()` + `pc13_toggle()` 配置 PC13 推挽输出，主循环中周期翻转。它只证明代码在持续运行，不证明 EEPROM 写入成功。
- **打开 GPIOB 时钟**：`RCC->APB2ENR |= RCC_APB2ENR_IOPBEN`。本课只开 GPIOB 时钟，不开 `RCC_APB1ENR_I2C1EN`，因为根本不使用 I2C1 外设。

### 7.2 本课新增步骤

以下步骤是软件 I2C 特有的，每步都需要说清硬件后果。

#### 7.2.1 PB6/PB7 开漏配置

```c
GPIOB->CRL |= GPIO_CRL_MODE6 | GPIO_CRL_CNF6 |
              GPIO_CRL_MODE7 | GPIO_CRL_CNF7;
```

`MODE=11`（50MHz 输出模式），`CNF=11`（开漏输出）。这里用的是**通用**开漏输出（`CNF=11`），不是复用开漏（`CNF=11` 在 CRL 中通用和复用开漏都是 11，但在 CRH 中不同——不过 PB6/PB7 在 CRL 中，`CNF=11` 就是开漏输出）。关键在于它不是推挽：写 1 时引脚被释放，由上拉电阻拉高；写 0 时引脚被拉低到 GND。

**硬件后果**：如果错配为推挽（`CNF=10`），SDA 在第 9 个时钟无法被从机拉低，从机即使发 ACK 也无法在电气上表现出来。更严重的是，如果主机坚持推高而从机拉低，两者直连短路，轻则通信异常，重则损害 IO。

#### 7.2.2 释放总线

```c
SDA_HIGH();  /* GPIOB->BSRR = GPIO_BSRR_BS7 */
SCL_HIGH();  /* GPIOB->BSRR = GPIO_BSRR_BS6 */
```

初始化 GPIO 后立即释放两根线。在开漏模式下，这两条语句不是"推高"，而是"关闭下拉管"，让外部上拉电阻把总线拉到高电平。

**硬件后果**：总线空闲状态必须是 SCL 高 + SDA 高。如果释放后 SCL/SDA 不是高电平，说明上拉电阻缺失、接线错误、模块未供电，或某个器件异常拉低了总线。此时后续所有 I2C 操作从一开始就无效。

#### 7.2.3 `i2c_start()`

```c
sda_release();   /* 确保 SDA 初始为高 */
scl_release();   /* 确保 SCL 初始为高 */
soft_i2c_delay();
sda_low();       /* SCL 高时 SDA 从高→低：产生 START */
soft_i2c_delay();
scl_low();       /* 拉低 SCL，为后续数据位做好准备 */
```

START 条件是 SCL 高电平时 SDA 从高跳变到低。代码中先保证 SDA 和 SCL 都是高，然后拉低 SDA，最后拉低 SCL。

**硬件后果**：必须在 SCL 高时执行 SDA 下降沿，AT24C02 才识别为起始条件。如果 SCL 和 SDA 释放顺序反了，或 SDA 下降沿发生时 SCL 不是高，从机不会进入接收状态，后续地址字节被忽略。

#### 7.2.4 `i2c_stop()`

```c
sda_low();       /* 确保 SDA 初始为低 */
scl_release();   /* 拉高 SCL */
soft_i2c_delay();
sda_release();   /* SCL 高时 SDA 从低→高：产生 STOP */
soft_i2c_delay();
```

STOP 条件是 SCL 高电平时 SDA 从低跳变到高。先保证 SDA 低，再拉高 SCL，最后释放 SDA。

**硬件后果**：STOP 告诉 AT24C02 本次传输结束，可以开始内部写周期。如果 STOP 没发出，EEPROM 可能认为传输还在继续，或总线一直被占用（`BUSY`），影响下次通信。

#### 7.2.5 `i2c_write_byte()`

```c
for (uint8_t i = 0; i < 8; i++) {
    if (b & 0x80U) SDA_HIGH(); else SDA_LOW();
    SCL_HIGH();       /* SCL 高：从机采样 SDA */
    soft_i2c_delay();
    SCL_LOW();        /* SCL 低：准备下一位 */
    b <<= 1;
}
```

每次取出字节的最高位放到 SDA，然后产生一个 SCL 高脉冲让从机采样。I2C 规定高位先发，所以 `0xA0`（二进制 `10100000`）会从 MSB 到 LSB 依次出现在 SDA 上。

**硬件后果**：如果 `for` 循环次数不是 8 次（比如手误写成 7），字节只发了 7 位，第 8 位缺了，从机收到的地址字节就是错的。如果 SDA 数据在 SCL 上升沿之后才变化（顺序反了），从机采到的是旧值而不是目标位。

#### 7.2.6 第 9 个时钟

8 位数据发完后，代码进入 ACK 时钟阶段：

```c
sda_release();     /* 释放 SDA，让从机可以拉低 */
soft_i2c_delay();
scl_release();     /* 第 9 个时钟高电平，从机在此窗口内 ACK */
soft_i2c_delay();
scl_low();
```

当前版本只释放 SDA 并给出时钟，没有读取 `GPIOB->IDR` 检查从机是否真的拉低了 SDA。所以本课代码没有 ACK 校验。

**硬件后果**：即使没有读 ACK，第 9 个时钟也必须存在——这是 I2C 协议规定的，缺了它从机的状态机可能错乱。完整软件 I2C 需要在 `scl_release()` 之后、`scl_low()` 之前执行 `GPIOB->IDR & GPIO_IDR_IDR7`。读到 0 表示 ACK，读到非 0 表示 NACK。由于 F103 开漏模式写 1 = 释放，不需要把 PB7 临时切换为输入模式，保持开漏输出并写 1 后读 IDR 即可。

#### 7.2.7 `main()` 写序列

```c
i2c_start();
i2c_write_byte(0xA0U);   /* 器件地址 + 写位 */
i2c_write_byte(0x00U);   /* EEPROM 内部地址 */
i2c_write_byte(0x5AU);   /* 要写入的数据 */
i2c_stop();
```

主循环每约 1 秒执行一次完整写序列，然后翻转 PC13。

**硬件后果**：序列发送完成且每字节都有第 9 个时钟，但因为没有 ACK 读取和读回校验，MCU 并不知道 EEPROM 是否真的接收了数据。这是本课代码最重要的边界——你能从逻辑分析仪上看到正确的 I2C 波形，但确认写入成功需要额外验证步骤。

## 8. HAL 版代码逐步讲解

### 8.1 已学步骤（快速过）

- **`HAL_Init()` 和 SysTick**：HAL 版调用 `HAL_Init()` 初始化 HAL 库，并提供 `SysTick_Handler()` 调用 `HAL_IncTick()`，使 `HAL_Delay()` 可用。与寄存器版不同，HAL 版的主循环通过 `HAL_Delay(1000)` 控制 1 秒间隔。
- **`system_clock_72mhz_init()` 和 `pc13_led_init()`**：与寄存器版功能相同，只是改为通过 `RCC_OscInitTypeDef` / `RCC_ClkInitTypeDef` 和 `GPIO_InitTypeDef` 配置，底层寄存器操作由 HAL API 封装。

### 8.2 本课新增步骤

#### 8.2.1 `soft_i2c_gpio_init()`

```c
gpio.Pin = SCL_PIN | SDA_PIN;
gpio.Mode = GPIO_MODE_OUTPUT_OD;
gpio.Pull = GPIO_PULLUP;
gpio.Speed = GPIO_SPEED_FREQ_HIGH;
HAL_GPIO_Init(GPIOB, &gpio);
```

`GPIO_MODE_OUTPUT_OD` 对应寄存器版的 `CNF=11`（开漏输出）。`GPIO_PULLUP` 启用内部上拉电阻，但工程上更推荐外部 4.7k 上拉。

**硬件后果**：`GPIO_MODE_OUTPUT_OD` 直接映射到 `GPIOB->CRL` 的 `CNF=11`。如果误写成 `GPIO_MODE_OUTPUT_PP`（推挽），SDA 在第 9 个时钟无法被从机拉低，电气冲突可能导致 IO 损坏。

#### 8.2.2 `scl_write()` / `sda_write()` 封装

```c
static void scl_write(GPIO_PinState state)
{
    HAL_GPIO_WritePin(GPIOB, SCL_PIN, state);
}

static void sda_write(GPIO_PinState state)
{
    HAL_GPIO_WritePin(GPIOB, SDA_PIN, state);
}
```

这两个函数把对单根线的 GPIO 写封装成一步，对应寄存器版的 `SDA_HIGH()` / `SDA_LOW()` / `SCL_HIGH()` / `SCL_LOW()` 宏。延时不在这里，而由调用方在合适位置显式调用 `i2c_delay()`。

**硬件后果**：`HAL_GPIO_WritePin()` 在底层操作 `GPIOB->BSRR/BRR` 寄存器，与寄存器版完全相同。区别只是 API 形式——SET 对应 BSRR 写 1（释放），RESET 对应 BRR 写 1（拉低）。延时不在这些函数里，保证了电平变化始终发生在精确的位置。

#### 8.2.3 HAL 版 START/STOP

`i2c_start()` 和 `i2c_stop()` 的时序与寄存器版完全一致，只是把宏调用换成了 `sda_write()` / `scl_write()`。HAL 没有使用 `HAL_I2C_*` 函数，因为本课故意不用硬件 I2C 外设。

**硬件后果**：START 和 STOP 的时序逻辑与寄存器版完全等价。如果 `sda_write(GPIO_PIN_SET)` 和 `scl_write(GPIO_PIN_SET)` 的执行顺序乱了（如先拉低 SDA 再拉高 SCL），从机不会正确识别起始或停止条件。

#### 8.2.4 HAL 版写字节

HAL 版 `i2c_write_byte()` 同样高位先发，每一位经历 SCL 低设置 SDA → SCL 高采样 → SCL 低结束。与寄存器版唯一的区别是把 `SDA_HIGH/LOW` 和 `SCL_HIGH/LOW` 宏替换为 `sda_write()` 和 `scl_write()` 函数调用。

#### 8.2.5 当前 HAL 版同样没有 ACK 判断

HAL 版第 9 个时钟释放 SDA，但没有调用 `HAL_GPIO_ReadPin()` 读取 ACK。它和寄存器版的边界完全一致——都有第 9 个时钟，都不检查从机应答。

如果要补 HAL 版 ACK，思路和寄存器版一样：
1. `HAL_GPIO_WritePin(GPIOB, SDA_PIN, GPIO_PIN_SET)` — 释放 SDA
2. 拉高 SCL — 让 ACK 位进入采样窗口
3. `HAL_GPIO_ReadPin(GPIOB, SDA_PIN)` — 读到 `GPIO_PIN_RESET` 表示 ACK
4. 拉低 SCL — 结束第 9 个时钟

这也说明 HAL GPIO 只是换了一种写法，不会自动把软件 I2C 变成完整协议栈。START、STOP、数据位、ACK、超时、总线恢复都由你自己设计。

#### 8.2.6 `HAL_Delay(1000)`

主循环每秒发送一次写序列并翻转 LED。与寄存器版的 `delay_cycles(7200000)` 不同，`HAL_Delay()` 基于 SysTick 中断，精度更高且不受编译优化影响。

**硬件后果**：LED 翻转只说明主循环持续运行、`HAL_Delay()` 正常计数，不能说明 EEPROM 写成功。这与寄存器版完全一致。

#### 8.2.7 内部上拉 vs 外部上拉

HAL 版配置了 `gpio.Pull = GPIO_PULLUP`，这能在释放时让引脚回到高电平。但 STM32 内部上拉阻值约 40kΩ，上升沿较慢，线长稍长或总线电容稍大时，I2C 波形可能变钝。

工程上更推荐在 SCL/SDA 上接 4.7k 左右外部上拉。内部上拉适合入门验证，外部上拉适合可靠通信。逻辑分析仪上高电平上升很慢、ACK 偶尔失败、速度稍高就不稳定时，优先检查上拉。

#### 8.2.8 软件 I2C 的超时意识

本课代码没有做超时处理。真实软件 I2C 不应该无限等待或盲目发送，因为总线可能被从机拉低、接线可能断开、ACK 可能失败。

完整驱动里，START 前应检查总线是否空闲，写字节后应检查 ACK，必要时产生若干 SCL 脉冲尝试释放被卡住的 SDA。否则一次异常就可能让后续通信都看似"没反应"。

## 9. 两个版本真正应该怎么学

寄存器版看 GPIO 寄存器怎样直接改变引脚电平；HAL 版看同样的引脚动作如何被 API 封装。

两者都没有使用 I2C1 外设，所以不要拿 `I2C1->SR1`、`HAL_I2C_Mem_Write()` 来解释本课代码。本课重点是“协议波形可以由软件手工产生”。

## 10. 检验问题清单

### 10.1 软件 I2C 为什么能工作？

**答**：因为 I2C 从机识别的是 SCL/SDA 上符合协议的电平时序。只要 GPIO 按规则产生 START、地址、数据、ACK 时钟和 STOP，从机就能识别。

### 10.2 为什么 `SDA_HIGH()` 叫释放 SDA 更准确？

**答**：PB7 是开漏输出，写 1 时并不是强推高，而是关闭下拉管，让上拉电阻把 SDA 拉高。

### 10.3 当前代码有没有判断 ACK？

**答**：没有。代码给出了第 9 个时钟并释放 SDA，但没有读取 SDA 电平判断从机是否拉低。

### 10.4 LED 翻转能证明 EEPROM 写成功吗？

**答**：不能。LED 翻转只能证明主循环在运行。写成功需要 ACK 判断、读回校验或逻辑分析仪确认。

### 10.5 为什么每位要先设置 SDA 再拉高 SCL？

**答**：I2C 从机通常在 SCL 高电平期间采样 SDA。先放好数据再拉高 SCL，才能让从机读到稳定电平。

### 10.6 软件 I2C 的速度由什么决定？

**答**：由 CPU 执行速度和延时循环决定。系统时钟或编译优化变化都会影响实际 SCL 频率。

### 10.7 HAL 版使用的是硬件 I2C 吗？

**答**：不是。HAL 版只用 HAL GPIO API 控制 PB6/PB7，并没有调用 `HAL_I2C_*`。

### 10.8 如果要补 ACK，应该怎么做？

**答**：发送 8 位后释放 SDA，在 SCL 高电平期间读取 SDA；低电平表示 ACK，高电平表示 NACK。

## 11. 工程实现步骤

### 11.1 需求分析

本课目标是理解 I2C 波形本身，不是做完整 EEPROM 驱动。因此代码保持最小：只产生写序列并用 LED 表示循环节奏。

### 11.2 硬件核查

确认 PB6/PB7 连接 AT24C02 SCL/SDA，模块供电 3.3V，GND 共地，SCL/SDA 有上拉。

### 11.3 寄存器路线

打开 GPIOB，配置 PB6/PB7 开漏输出，用 `BSRR/BRR` 实现拉低和释放，再手写 START、STOP、写字节。

### 11.4 HAL 路线

用 `GPIO_InitTypeDef` 配 PB6/PB7 为 `GPIO_MODE_OUTPUT_OD`，用 `HAL_GPIO_WritePin()` 按同样时序控制两根线。

### 11.5 工程思维

软件 I2C 适合救急、调试或引脚不够灵活时使用。正式项目要考虑 CPU 占用、时序精度、ACK/超时、总线恢复和多设备冲突。

它的最大优点是透明：每一次 SCL/SDA 变化都在你的代码里，适合用来学习协议和排查硬件。它的最大缺点也是透明：所有时序都靠 CPU 执行，主循环一忙、关中断时间一长、编译优化一变，I2C 速度都可能变化。

所以软件 I2C 不应只追求“能发波形”。工程版本至少要有 ACK 判断、超时、读回校验和错误返回值。只有这样，上层代码才能知道 EEPROM 是真的写成功，还是只是 MCU 自己把波形发出去了。

### 11.6 常见工程陷阱

不要把“释放高电平”理解成“推挽输出高”。不要用 LED 翻转替代通信校验。不要忘记 ACK 需要读取 SDA，不是只产生第 9 个时钟。

## 12. 运行现象

下载后 PC13 会按约 1 秒间隔翻转。若接了逻辑分析仪，PB6/PB7 上能看到周期性 I2C 写序列：起始、`0xA0`、`0x00`、`0x5A`、停止。

如果 EEPROM 接线正确且时序足够，它可能被写入 `0x5A`；但当前代码没有读回验证。

## 13. 常见问题排查

### 13.1 PC13 不翻转

先查程序是否下载成功、PC13 是否为低电平亮、GPIOC 时钟和模式是否正常。

### 13.2 逻辑分析仪看不到 SCL/SDA

检查 PB6/PB7 是否接错、GPIOB 时钟是否打开、探头地线是否共地。

### 13.3 SCL/SDA 高电平上不去

检查上拉电阻、模块供电、是否有器件长期拉低总线。开漏输出释放后必须能回到高电平。

### 13.4 EEPROM 没写进去

当前代码不判断 ACK，也不等待写周期和读回。先补 ACK 读取，再加写后延时和读回校验。

如果 ACK 正常但读回不对，再检查 AT24C02 地址脚 A0/A1/A2 是否和 `0xA0` 匹配。`0xA0` 对应常见 7 位基地址 `0x50` 左移后的写地址，地址脚状态改变后，器件地址也会改变。

还要注意 EEPROM 页写规则。AT24C02 通常有页写限制，连续写跨页时地址会在页内回卷。本课只写一个字节，不涉及页回卷；后续扩展多字节写时必须单独处理。

### 13.5 波形太快或太慢

调整 `soft_i2c_delay()` 或 `i2c_delay()`。软件延时受系统时钟和编译优化影响，不能当精确定时器。

## 14. 本课最核心的结论

1. 软件 I2C 的本质是用 GPIO 手工产生 I2C 总线波形。
2. 开漏和上拉仍然是 I2C 的电气基础，软件模拟也不能跳过。
3. START、STOP、数据位和 ACK 都是 SCL/SDA 的具体电平关系。
4. 当前代码只演示发送写序列，没有验证 ACK 和读回结果。
5. HAL GPIO 版不是硬件 I2C，只是把 GPIO 写寄存器换成 API。
6. 理解软件 I2C 后，硬件 I2C 的状态标志会更容易理解。

## 15. 建议你现在怎么读这节课

先用纸画出 START、发送 `0xA0`、ACK 位和 STOP 的 SCL/SDA 波形。再对照 `i2c_write_byte()` 看每一次宏调用对应波形上的哪一段。最后用逻辑分析仪验证代码产生的波形。
